## risks
- R1 Closure volume dominates the effort and is error-prone. Roughly 2,000+ hand-ported Lua closures: ModParser specialModList ~1,025, modTagList ~136, preFlagList 7, jewel funcs 64-69 (which are runtime closures stored inside mods); ConfigOptions 531; skills 133; CalcTriggers configTable 82; ModMap 41; plus the mirage pre/post funcs. A literal translation will drift silently.
- R2 Shared contracts across parallel agents. calcs.offence (~5.9k lines), calcs.perform (~2.7k) and buildDefenceEstimations (~2.2k) are single functions with hundreds of shared locals. Without frozen Env/Actor arena, OffenceCtx/PerformCtx, Output/Breakdown, ActiveSkill/skillCfg (with layered skillCond) and ModDb APIs, each agent will invent its own and the pieces will not compose.
- R3 Lua semantics leaking into numbers: only nil and false are falsy (0 is truthy); `x or 0`; `a and b or c`; ipairs stops at holes (createActiveSkill); pairs() hash order affects mod insertion order and so Override/List/first-match results (26 pairs loops in CalcSetup; ControlHost draw and hit-test order); ModParser scan tie-break; MORE rounded to 2 decimals per name unless highPrecisionMods; floor(x/div+0.0001); ceil_b; 32-bit signed bit ops.
- R4 Recursive calc with a global cache. buildActiveSkill runs a fresh initEnv plus perform per skill for triggers, mirages and cost warnings. GlobalCache.cachedData stores whole Env and ActiveSkill objects that other envs read. The calc also mutates build state (socketGroupList, srcInstance.skillPart, node.conqueredBy, jewelData.limitDisabled). A pure Rust function needs an explicit normalise phase and cache snapshots. A stale cache gives silently wrong DPS.
- R5 Oracle gaps. The current parity tooling (pob_diff, run.sh) measures the OLD pob-engine. The oracle captures only scalar player/minion output keys. State leaks between builds loaded in one boot (corpus 031→051). Some corpus builds have TotalDPS=0 or FullDPS=0. mod_store.rs has never been compared against the oracle, and no mlua-to-Mod converter exists for stage dumps.
- R6 Data poisoning. Any reuse of data/skills/*.json or pob-data flags carries the stale SkillType numbering into support/skill-type matching. Closures in the existing JSON have no identity. The hand-copied constant tables (monster_tables.rs, jewel_radius.rs, timeless_jewels.json) are drifting from upstream.
- R7 Upstream drift. The port pins PoB 2.67.2. Every league changes Data, ModParser and calc. Without per-function provenance and change detection, the Rust port falls out of date within one league, and the 'DPS within a few %' target degrades even when the port was correct.
- R8 Performance of power and DPS-sort paths. The tree power report, GemSelectControl DPS sort, item stat diffs and the misc calculator re-run the calc per node or item. pob-calc's Tag has about 70 fields and is cloned per mod; names are String keys with a format! per query; every query goes through dyn EvalEnv. This may be slower than LuaJIT PoB at heatmap scale.
- R9 UI fidelity rests on unverified renderer details: font atlas selection and advance rounding, alpha of ^ escapes, whether a SetDrawLayer call with only a layer resets subLayer, CENTER/RIGHT measured against viewport width, gamma (Rgba8UnormSrgb vs gamma-space blending). Text width drives layout everywhere (labels, checkboxes, tooltips), so one metric error shifts whole screens.
- R10 Closure-heavy UI vs the borrow checker. 145 shown and 79 enabled closures, about 90 geometry closures, 72 tooltipFuncs, onClick/selFunc callbacks that mutate build state, anchors across hosts, duck-typed is-a checks. Without one arena + Prop + Action design decided first, every tab port will diverge.
- R11 Web target feasibility. TreeData is 552 MB; timeless plus abyss LUTs are about 300 MB of zips (GloriousVanity decompresses to a 52 MB .bin). wgpu 22 WebGPU is broken, so the build is forced onto WebGL2. pathofexile.com and the trade API block CORS, and an OAuth localhost redirect is impossible on the web. Web parity may be infeasible without a server or proxy and lazy asset streaming.
- R12 Migration and coexistence. The shipping app currently runs real PoB Lua through the worker, and the web build runs pob-engine. Deleting pob-engine breaks pob-ui (about 20 files), pob-extract timeless_nodes.rs and pob_diff. A long port with no shippable middle state risks stalling.
- R13 Upstream-of-calc parsers. Item.lua ParseRaw (~1,220 lines), ItemTools, PassiveTree ProcessStats, and PassiveSpec BuildAllDependsAndPaths (timeless, abyss, cluster subgraphs). If any of these differs, every downstream number drifts, and the final-output diff cannot tell you which one is wrong.

## recommendations
- Phase 0, before any calc port: build the oracle harness first. (a) Create a crate pob-oracle (dev-dependency only) that holds JitPob, one build per process or a fresh boot each time, so state does not leak between builds. (b) Write a converter from mlua tables to pob-calc Mod, mirroring mod_parser::lua_to_mod. (c) Add stage dumps via HEADLESS_EXEC-style snippets: modDB/enemyDB after initEnv, activeSkillList with skillTypes/skillFlags/skillData, skillModList per skill, output after defence/offence/triggers, plus env.player.output nested MainHand/OffHand. (d) A new pob_calc_diff that writes {build,pob,ours} so scripts/parity/report.py works unchanged. (e) A curated DPS subset of the corpus where TotalDPS > 0, plus per-skill DPS dumps over calcsTab skill outputs.
- Phase 0: regenerate ALL enums (SkillType, ModFlag, KeywordFlag) from Data/Global.lua with codegen. Delete the three hand copies (pob-data/flags.rs, pob-calc/flags.rs, pob-extract/main.rs:374-591). Treat data/skills/*.json as invalid until the Data.lua-based dumper replaces it.
- Phase 0: write and freeze the shared contracts doc plus type stubs before parallel work. Env/Actor/DbId arena; ActiveSkill with skillCfg and a layered SkillCond; Output (an OutVal enum with num_or_zero and get_opt, Lua truthiness); Breakdown; PerformCtx; OffenceCtx; GlobalCache with CachedSkill snapshots and the limitedSkills guard; a normalise-build phase separating the build-state mutations; a Lua-semantics helper module (round, floor_b/ceil_b, the +0.0001 floors, printf %g). Do this as pob-calc-lua work units U00/U01/U13, done first and done serially.
- Do a thin vertical slice before scaling out. One simple build (no auras, one attack, one weapon) through ModParser via the ModCache lookup, then Item.BuildModList, PassiveTree ProcessStats, initEnv, perform (attributes and pools only), offence (hit/speed/crit/TotalDPS), compared against the oracle at each stage. This proves the contracts, the oracle and the performance budget before thousands of lines are ported against them.
- ModParser: use ModCache.lua (23,207 lines) loaded as data at runtime as the first-tier parser immediately, which makes the calc independent of ModParser on day one. Then port ModParser with lua_pattern.rs, keeping the pattern tables verbatim. Add a semi-automatic Lua-to-Rust transpiler for the ~1,026 static entries and the ~700 one-line `function(num) return { mod(...) } end` closures. Gate it with tests/modcache_oracle.rs at 99.9% or better, and widen the oracle by running PoB's ModParser over every stat line in Mod*.lua, Uniques, all tree versions, tattoos and cluster notables at extract time.
- Closure provenance and change detection everywhere. Dump each Lua function as {path, file:line range, body hash} for skills, specialModList, modTagList, jewel funcs, ConfigOptions apply, ModMap apply, the CalcTriggers configTable and the mirage funcs. Have a registry check (build.rs or CI) that every id has a Rust impl whose recorded hash matches upstream. Extend the same idea per function to Calc*.lua: store a 'ported from <upstream sha>:<file>:<lines>' header in each Rust fn and add a CI script that diffs upstream ranges on a PoB bump.
- Fix the known mod_store.rs gaps first: ScaleAddMod/ScaleAddList (critical for aura and buff DPS), CopyList, Combine, MergeMod/MergeNewMod, no globalLimits on ModList stores, and the parent recursion in Replace/ConvertMod. Then run a per-build oracle test that compares Sum/More/Flag/Override/List/Tabulate/EvalMod over dumped player, enemy and skill DBs across a cfg matrix. Intern mod names and slim Tag into per-type payloads early, while there is only one consumer.
- Add explicit work units for the gaps: (1) the abyss LUT reader plus DataJewelFileLoader/DataLegionLookUpTableHelper inside the PassiveSpec port; (2) GameVersions plus the tree-version convert flow, and add legacy trees 2_6/3_6-3_9 to the tree dump; (3) ItemTools.lua bundled with Item.lua; (4) build XML I/O compatible with runtime/lua/xml.lua, with a round-trip test (Rust save, LuaJIT PoB load, identical outputs); (5) dkjson/sha replacements; (6) ModMap apply closures owned by the config unit; (7) PearlSupports in the data dump.
- UI de-risk. Instrument the LuaJIT oracle to replace SimpleGraphic globals (SetDrawLayer, SetViewport, SetDrawColor, DrawImage, DrawImageQuad, DrawString, DrawStringWidth) with recorders. Then feed scripted input events and diff draw-command streams between PoB and the Rust UI per frame; no golden images needed. DrawStringWidth still needs a real implementation inside the oracle, so port the font engine first and verify it against the PoB-SimpleGraphic v2.5.4 r_font.cpp source, fetched from GitHub. Scope sg-core to the APIs PoB actually calls: no LoadArt*/StackTextures/SetBlendMode.
- Decide the UI framework once (unit U3 in the pob-ui-lua map): a global slotmap arena of controls, Prop<T>, Anchor with collapse, Widget trait with Focus, Action-queue callbacks, insertion-ordered hosts. Port NotesTab end to end as the first proof before any agent starts on a large tab. Use winit plus a current wgpu directly and drop eframe 0.29, which pins wgpu 22. Use Rgba8Unorm textures and a non-sRGB surface to match SimpleGraphic's gamma-space blending.
- Strangler migration. Keep the current Lua-backed app shipping. Add a hidden 'Rust calc' mode that runs the Rust calc beside PoB's Lua on the same build and shows per-key diffs in-app, so real user builds become test cases. Retire pob-engine only after moving inflate_timeless_lut, share-code encode/decode and resolve_share_url into a small pob-io crate (used by pob-extract and the new UI). Decide early whether web is in scope; if it is, plan lazy HTTP asset and LUT streaming plus a CORS proxy.
- Performance budget. On the vertical slice, measure full calc time and the misc-calculator (CALCULATOR mode, cached parent DBs) time per node against LuaJIT PoB. Set a target (e.g. at least LuaJIT speed for the power report over about 1,300 nodes) before the ModDb design is locked in.
