KEY DATA STRUCTURES:
- env: build, data, configInput/placeholder, calcsInput, mode (MAIN/CALCS/CALCULATOR), mode_buffs/combat/effective, buildBreakdown, spec, override, classId, modDB/enemyDB/itemModDB, enemyLevel, player/enemy/minion actors, radiusJewelList, extraRadiusNodeList, allocNodes, grantedPassives, grantedSkills*, flasks, tinctures, itemWarnings, requirementsTable*, auxSkillList, limitedSkills, partyMembers, and CALCS-mode *Used tables.
- actor: modDB, level, output, breakdown, itemList[slot], weaponData1/2, mainSkill, activeSkillList, enemy, parent, player back-pointers, minionData, plus many ad-hoc fields. The graph is cyclic; ModStore reaches actors via modDB.actor and getActor(tag.actor).
- activeSkill: activeEffect, supportList, effectList, actor, socketGroup, summonSkill, skillTypes (set of SkillType ints), minionSkillTypes, skillFlags (dynamic string set), skillData (dynamic string to value), skillModList, skillCfg, weapon1Cfg/weapon2Cfg, buffList, minion, mirage, skillPart/skillPartName, disableReason, conversionTable, infoTrigger.
- skillCfg: flags, keywordFlags, skillName, skillId, skillGem, skillPart, skillTypes, skillCond (layered via setmetatable __index; CalcActiveSkill 482/487, CalcOffence 4422/4695/5000), slotName, skillStats, summonSkillName, source, actor.
- output: string-keyed; 587 distinct literal keys in Calc*.lua plus 432 sites that build keys with `..` concatenation. Values are mostly numbers, but also booleans, strings (PierceCountString, FortificationEffect "0") and nested tables: MainHand/OffHand per-pass outputs, Minion, SkillDPS list, *WarningList.
- breakdown: same keys. Values are line lists or tables with rowList/colList/slots/reservations/damageTypes/modList/label/footer. It is built only when env.buildBreakdown is true. The UI (Classes/CalcBreakdownControl.lua) also calls modDB/skillModList:Tabulate after the calc, so actors' DBs must outlive the calc.
- cache: GlobalCache.cachedData[mode][uuid], uuid = cacheSkillUUID (name_slot_gemIdx_groupIdx). An entry holds Speed/HitSpeed/costs/CritChance/TotalDPS plus ActiveSkill and the whole Env. Readers use .Env.player.output[arbitraryKey] and .ActiveSkill.skillData/skillModList (CalcPerform 31, CalcTriggers 70-593, CalcMirages 127-364). It is filled by recursive calcs.buildActiveSkill (fresh initEnv plus perform) and cleared by Build.lua wipeGlobalCache.
- Env reuse: calcFullDPS runs perform repeatedly on one env (perform must be idempotent given wipeEnv/accelerate); the misc calculator returns a closure with cached player/enemy/minion DBs as parents (specCopy).

ModDB QUERY VOLUME: 1,969 :Sum/:More/:Flag/:Override/:List/:Max/:Min/:Tabulate/:HasMod call sites in Calc*.lua, many with computed names (damageType.."Min"). 1,357 distinct mod names appear in ModCache.

## risks
- Output and modDB ordering: mods are inserted in pairs() order in several places (CalcSetup has 26 pairs loops, e.g. over env.allocNodes, buffs, curses and ailments). Override, List and 'first match wins' results depend on insertion order, and LuaJIT hash order is not reproducible in Rust. Expect rare oracle mismatches; where order matters, sort keys (node id, slot name) and verify against the oracle.
- ModParser scan() picks the best match over pairs(patternList), breaking ties by start index, end index and pattern length. Full ties fall back to hash order. The ModCache oracle will catch these; resolve them per case.
- Recursive calc: perform calls buildActiveSkill, which runs a fresh initEnv and perform for other skills (triggers, mirages, cost warnings) and stores whole Env and ActiveSkill objects in GlobalCache. These are cross-env object references (mirages copy a skill from another env). Rust needs Rc<Env> snapshots or explicit extracted CachedSkill structs, plus limitedSkills recursion guards. Cache invalidation is driven by Build.lua wipeGlobalCache, so a stale cache gives silently wrong DPS.
- The calc writes into build state: activeEffect.srcInstance.skillPart/skillPartCalcs, supportEffect.isSupporting, build.skillsTab.socketGroupList (granted-skill groups added in MAIN mode, CalcSetup 1452-1565), build.skillsTab.displayGroup, item.jewelData.limitDisabled, and PassiveSpec node.conqueredBy. A pure-function Rust calc needs a separate 'normalize build' phase, or &mut Build.
- EvalMod mutates shared tags (tag.div = GetMultiplier(...) at ModStore ~line 335) and copyTable is used everywhere to avoid aliasing. In Rust, keep tags immutable and compute locally, then verify no behavioural reliance on the mutation.
- Lua nil, false and 0 semantics: `output.X or 0`, `a and b or c` with a falsy b, `if output.X then` (0 is truthy in Lua!), and ipairs stopping at holes (createActiveSkill sets rejectedSupportsIndices[index]=nil while iterating). Literal translation is error-prone; the Output API needs both get_opt and num_or_zero, and truthiness must follow Lua rules (only nil and false are falsy).
- Closures that must be hand-ported: about 1,025 in specialModList, 136 in modTagList, 69 jewel funcs (runtime, stored in mod values as JewelFunc/ExtraJewelFunc), 531 config apply closures, about 133 skill-data funcs, 82 trigger configTable entries, and mirage pre/post funcs. Together this is over 1.9k closures, which dominates the porting effort beyond the main calc files.
- Very long single functions (calcs.offence about 5.9k lines, calcs.perform about 2.7k, buildDefenceEstimations about 2.2k) share hundreds of locals across the sections that become separate work units. Each unit's agent needs a shared 'locals context' struct agreed up front (e.g. OffenceCtx { output, breakdown, skill_mod_list, skill_cfg, skill_flags, skill_data, pass_list, can_deal, ... }), or the agents will diverge.
- Breakdown text uses Lua string.format (%g, %.2f, %d, %s with ^7/^8 colour codes). Rust needs a printf-compatible %g implementation. It does not affect DPS, but it affects the calcs-tab parity UI.
- Numerics: ModDB:More rounds each name group's product to 2 decimals unless data.highPrecisionMods says otherwise, Multiplier tags use floor(base/div + 0.0001), and server-tick rounding uses ceil_b. These must be reproduced exactly. f64 parity is otherwise straightforward (LuaJIT numbers are doubles; bit ops are 32-bit signed, and all flags fit in u32).
- The CalcBreakdownControl UI queries actor.modDB / mainSkill.skillModList with Tabulate after the calc, so the Rust env (or at least the DBs) must be retained after the calc finishes for the calcs tab.
- Item.ParseRaw (1,220 lines of Lua-pattern text parsing) and PassiveSpec.BuildAllDependsAndPaths (timeless LUTs, cluster subgraphs) sit upstream of the calc. If these are not ported faithfully, the mod lists differ and every downstream number drifts.
- pob-calc/src/mod_store.rs has only 4 unit tests and is unused at runtime. Its fidelity is unverified until diffed against the oracle (Sum/More/Flag/Override/List/Tabulate on dumped player DBs from the corpus).
